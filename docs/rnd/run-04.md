## Focused independently reproduced failures

Ran six bounded paired-process probes against the preserved JAR, with fixtures only under **`E/evaluator-probes/`**. Original `uploads` were unchanged. Each directory retains input, both stdout/stderr streams and, where relevant, a stdout diff; `results.json` records exits and lengths. Stopped further source auditing after these sufficient counterexamples.

| Probe | Native versus Java | Finding |
| --- | --- | --- |
| `quit`: `n\nquit\ny\n` | Both 997 stdout bytes, empty stderr, exit 0 | Positive strict control. |
| `eof-game`: `n\n` | Both 762 stdout bytes, exit 0; stderr **454 vs 0** | ENDFILE diagnostic entirely absent. |
| `record121`: `n\n` + 121 `x` bytes + LF | Both 762 stdout bytes, exit 0; stderr **671 vs 0** | RECORD diagnostic entirely absent. |
| `double-blank`: `\n\nn\nquit\ny\n` | Exit 0 and empty stderr both; stdout **999 vs 997 bytes** | Java loses one native space-only output record. This is a gameplay/input-output mismatch on unchanged data, not a PID issue. |
| `missing-data`: absent database in fresh fixture cwd | Both print 16-byte initialization; native exit **0**, Java **1** | Uncaught `NoSuchFileException`; termination differs independently of diagnostic formatting. |
| `decimal-section`: copied data's first eight-byte numeric field changed from `1       ` to `1.0     ` | Native completes normal 997-byte quit transcript, exit **0**; Java prints 16 bytes then `NumberFormatException`, exit **1** | Native numeric input accepts decimal section value; Java `Integer.parseInt` rejects it. Copied-data parser fidelity failure, not an altered acceptance test. |

Root-cause evidence in the delivered source:

- `Main.main` silently catches `Terminal.EndOfInput | Terminal.InvalidRecord`; no stderr renderer. Startup `GameData.load` executes outside that catch and exceptions escape.
- `Terminal.nextWords` repeatedly discards every zero-length record using `do ... while (record.isEmpty())`; the two-blank probe demonstrates that this does not match native record handling/output.
- `GameData.number` labels itself F(8) conversion but delegates directly to `Integer.parseInt`; the numeric fixture disproves that equivalence.

The known native-report gap is real, but **not the only remaining defect**. Differing PID values do not explain zero Java diagnostics, missing blank output, numeric conversion or exit-status failures. No original requirement was proved impossible; the prior [diagnostic-contract investigation](diagnostic-contract.md) still applies. Do not excuse omissions on that basis.

## Conclusion and next action

One live swarm and one invocation were respected; recorded cost was **$21.45 including parent**, but benchmark completion failed. The generated implementation passes many useful checks, yet a green documented test command overstates fidelity because it ignores stderr, and additional small probes find concrete semantic defects. This is not an exhaustive audit or a production-readiness claim.

Before another model comparison: preserve the full-stream oracle and make unresolved findings actionable inside the same invocation, distinguish diagnostic compatibility work from invented impossibility, and serialize/fingerprint final builds. A smaller alternative is to change only the acceptance evidence standard first; it will prevent misleading green summaries but will not itself repair gaps. To test Opus behavior, use a separately labeled future run with verified successful Opus worker usage; this fallback run cannot answer that question.
