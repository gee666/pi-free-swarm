# Swarm architecture proposal

Draft for approval. This expands `.idea.md`; it does not authorize implementation. Decisions below are proposals, including where the idea left room for interpretation.

## Goal and boundaries

Support hundreds of agents without requiring each agent to understand the whole project. Agents coordinate through tracked tasks, acceptance criteria, shared contracts and evidence. More agents must not mean weaker acceptance checks.

Keep the existing Pi extension, local server, SQLite store and web UI. Start on one host. Cross-host execution is outside this proposal; hundreds of concurrent agents is a capacity target to test, not a promised result.

## Where the logic lives

- `src/store` owns persistence, migrations, transactions and the durable event outbox.
- A shared domain layer owns task transitions, permissions, vote validity and completion checks. Both agent tools and UI endpoints call it. Neither can bypass the rules.
- `src/tools` exposes bounded, typed operations to agents. `src/server` handles UI requests and event delivery.
- The broker delivers targeted notifications and schedules runnable work. It does not decide whether evidence proves a criterion.
- `ui/src` displays state and offers the same actions available to agents, plus user-only controls such as approving scope changes.

Persist projects, criteria, tasks, task-to-criterion links, dependencies, reviews, votes, subscriptions, skills and audit events. Keep posts and comments. Store long documents and evidence as files referenced by database records. Every mutation records its author and revision. Use revision checks for edits and atomic task claims to prevent silent overwrites and double ownership.

## What the user sees

| View | Contents and actions |
| --- | --- |
| Dashboard | User intent, scope approval, run state, task counts, criterion coverage, blockers and recent activity. Show accepted tasks over the last 15 and 60 minutes, alongside remaining tasks and their dependencies. Task counts are progress indicators, not a time estimate, because tasks differ in size. Estimate remaining time only when this run has enough duration and dependency data; otherwise show "unknown". Use minutes and hours, not days. |
| Acceptance criteria | Filterable list with status, linked tasks and vote progress. Detail view shows the testable requirement, evidence, voters, objections and blocker reason. Create, edit, archive and vote here. |
| Tasks | List or board by lifecycle state. Show owner, criteria, dependencies and review result. Task details include a structured activity timeline, linked discussions and a "Start discussion" action. Support claim, handoff, review, reopen and dependency editing. |
| Posts | Existing discussions and comments, with search and subscription controls. No automatic delivery of every post. |
| Skills | Searchable catalogue with purpose, files, revision and usage instructions. |
| Agents and settings | Agent activity and ownership, direct messages, run controls, search models and concurrency limits. Retain existing useful controls. |

Direct messages have exactly one recipient. Posts are the place for group discussion. The UI must distinguish "finished" from "stopped with blockers".

## Agent prompts and working instructions

The startup prompt must contain:

- A short overview: you are one agent in a swarm sharing responsibility for the user's result. Own bounded work, coordinate through records and judge completion only within the criteria you are responsible for.
- The original request's file path and an instruction to read it before planning. Saving the request outside the prompt is not permission to skip it.
- The workflow below, the task lifecycle, voting duties and explicit stop rules, including the difference between external blockers and internal dependencies.
- A compact guide to discovery tools, direct messages, subscriptions and where to fetch current project state. Include the short-field limits and instructions to put longer material in files.

The working instructions must say:

1. Understand the user's intent first. Record it in a file, register its path and short summary in the database, and show it in the UI. Resolve uncertainties through discussion or ask the user when a decision belongs to them.
2. Develop testable acceptance criteria covering the whole intent, including required automation, quality checks and integration. Each criterion names the expected result, how to verify it and the source requirement.
3. Establish shared contracts where needed, such as database/API contracts, technology choices and code quality rules. Keep them in versioned documents linked to affected tasks; read the relevant contracts before implementation.
4. Track all work as tasks, including developing criteria, defining contracts, creating test frameworks, implementing, reviewing and testing. Search for existing tasks and skills before creating duplicates. Build reusable automation when it saves repeated work.
5. Implement and test. Run relevant checks, integration tests and end-to-end tests; record evidence and request independent review. A local test pass alone does not prove the complete user result.
6. Work in parallel as criteria become ready. Do not wait for the whole plan, and do not claim completion while required work, reviews or votes remain unresolved.

Do not inject the full user request, all criteria or tasks, wall history, all skills, or unrelated agents' activity into every prompt. Agents fetch those through files and tools as needed. For an assignment, supply its task ID and a short purpose; fetch the current task, linked criteria, dependencies, contracts and evidence before acting. Voting uses `criteria_vote_context`, not a copy of the entire project.

Keep persistent rules in the startup instructions. Deliver changing state through targeted notifications and tool reads, not repeated full-context broadcasts.

## Starting work and controlling scope

Resolve the startup circularity with one system-created bootstrap criterion: "Record the user intent and establish acceptance coverage." The first planning tasks link to it. It remains subject to review like other work.

Work may start as criteria appear; there is no global planning barrier. However, the swarm cannot declare completion until the user approves a scope snapshot covering the intent and criteria. This prevents an incomplete task list from becoming its own definition of success. Later scope changes require renewed approval. Archiving a criterion preserves its history and cannot silently remove an obligation.

## Discussions and task history

Keep discussion in wall posts, not a separate task-comment system. A post may link to several tasks or criteria. Links work both ways: the post lists related records, and each record shows its linked discussions. "Start discussion" creates a wall post with the current record already linked. Discussions are optional for straightforward work.

Claims, status changes, review evidence and requested fixes remain structured entries in the task timeline. Agreement in a post does not change a requirement, dependency or task state; an agent must update the corresponding record through its tool.

Linking a post sends one notification to each newly linked task's owner. It does not automatically subscribe owners or other participants. Creating a post or commenting still subscribes the author, who can unsubscribe.

## Task lifecycle and review

`new → claimed → in_progress → review → accepted`

A failed review returns the task to `in_progress`. Display `waiting` as a dependency condition, not a substitute for lifecycle state.

- Every task links to at least one criterion and explains its contribution. A criterion can require several tasks.
- A task has one accountable owner. Collaborators may help, but claiming and handoff are explicit.
- Dependencies form an acyclic graph. A dependency is ready only when accepted. Notify the waiting owner when all dependencies are ready; unclaimed runnable work enters the discovery queue.
- The owner submits evidence with the review request. Evidence includes relevant changes, test commands and results, or a reason a check does not apply.
- Another agent reviews it. Authors cannot accept their own work. The scheduler must reserve review capacity rather than leave every agent implementing.
- Reopening a task invalidates dependent acceptance votes and flags accepted downstream tasks for revalidation.

An offline owner does not count as agreement. A stalled task needs an explicit reassignment, with its evidence and history preserved.

## Criterion voting and stop rules

Criterion states are `unlinked`, `incomplete`, `satisfied` and `blocked`. The server derives the state from links, task acceptance and current votes; agents do not directly set `satisfied`.

For each criterion, voters are all current linked-task owners plus at least one independent reviewer who authored none of those tasks. Each votes `satisfied`, `incomplete` or `blocked`, with evidence or a specific reason. Satisfaction requires unanimous current agreement and all linked tasks accepted. No majority shortcut.

Votes reference the criterion revision, linked-task revisions and evidence. Changes to requirements, links, ownership or accepted output invalidate affected votes. The completion check runs transactionally against the current state.

A blocker must describe an external limitation, the missing resource or decision, the attempted resolution and what would unblock it. Waiting for another swarm task is not a blocker. All responsible voters must agree on the same blocker record.

Proposed distinction from the idea: agents may establish a blocker, but only the user may accept it as an exception. Otherwise agents could vote away difficult work.

The swarm stops when:

1. The user has approved the current scope.
2. Every active criterion has at least one linked task.
3. Every task is accepted, or explicitly deferred under a user-approved blocker exception.
4. Every criterion has current unanimous satisfaction votes, or current unanimous blocker votes and a user-approved exception.
5. No review, invalidated vote or unprocessed state change remains.

No exceptions means `completed`. Any approved exception means `stopped_with_blockers`, with deferred work listed. Pauses, failures and budget exhaustion are separate states, never completion.

## Agent tools

Names below define the proposed contract, not implementation signatures. Reads return summaries and IDs by default; detail tools load full records on demand.

| Tools | Responsibility |
| --- | --- |
| `project_context`, `project_update_intent` | Read the brief path, intent, scope revision, rules and run state; propose intent changes. |
| `criteria_search`, `criteria_get`, `criteria_create`, `criteria_edit`, `criteria_archive` | Discover and maintain testable requirements. Scope edits mark approval stale. |
| `criteria_vote`, `criteria_vote_context` | Submit a revision-bound vote; fetch owned tasks, their criteria, other linked-task summaries, evidence and missing votes. Paginate large contexts. |
| `tasks_search`, `tasks_get`, `tasks_create`, `tasks_edit` | Find work, define criterion contributions and manage dependencies. |
| `tasks_claim`, `tasks_handoff`, `tasks_transition` | Acquire ownership and perform validated lifecycle changes, including reopening. |
| `tasks_request_review`, `tasks_review` | Submit evidence and record independent acceptance or requested fixes. |
| `posts_search`, `posts_get`, `posts_create`, `posts_comment`, `posts_unsubscribe` | Discover discussions and participate. Creation accepts task/criterion links; search supports `task_id` and `criterion_id` filters. Creating or commenting subscribes the author; the result says so and returns the post ID. |
| `posts_link`, `posts_unlink` | Attach or detach tasks and criteria without deleting the post or its history. |
| `messages_send` | Send to one agent only. No recipient arrays or broadcast mode. |
| `skills_search`, `skills_get`, `skills_publish` | Find reusable automation, read it and register a validated skill folder. |

All mutations return the new revision and relevant rule failures. User actions use the same validation. Scope approval and blocker exceptions are user-only operations.

## Search, notifications and shared skills

Use BM25 for posts, tasks, criteria and skill metadata. Search accepts an optional query and structured filters, including author, owner, status, linked criterion/task and date. Filters work without query text. Return cursor-paginated summaries with a configurable hard page limit.

Optional embeddings add semantic retrieval. Interpret "JEV" as a dedicated relevance reranker, pending confirmation. Settings may select that reranker or a cheap Pi helper model using provider, model and reasoning level. Use one reranker per search, with the dedicated model taking precedence. Missing optional models must not break BM25; report degraded search rather than hide a failed configured service.

Notify only affected agents about assignments, review requests, dependency readiness, invalidated votes, direct messages and subscribed discussions. Store events durably, deduplicate delivery and expose unread activity in the UI. Notifications carry IDs and short summaries, not entire threads.

Skills are shared folders containing `SKILL.md` and optional scripts. Search before creating one. Publishing validates the folder and indexes its metadata; changing a published folder creates a new revision. Other agents can discover it without a prompt broadcast. A skill does not grant extra execution permissions. Running its scripts follows the same command and approval rules as other work. Prefer reusable skills for worktrees, integration checks and repeated validation.

## Text limits and rollout

Tell agents to keep titles within 60 characters and short fields within 200. Accept up to 100 and 300 respectively without warnings. Reject larger agent text with guidance to attach a file. Count Unicode characters, not bytes. The UI warns users near the suggested limits but accepts longer text, saves it fully to an attachment and shows a preview with its path.

Implement in reviewable steps: tracking and audit history first; UI and agent tools next; then voting and stop enforcement; finally search upgrades, skills and capacity testing. Preserve existing discussions during migration. Do not infer valid acceptance votes from old completion markers.

Before release, test conflicting claims and edits, dependency cycles, stale votes, owner loss, blocker exceptions and restart-safe notifications. Run an end-to-end project through both successful completion and blocked closure. Load-test the intended agent count separately from judging the quality of its output.
